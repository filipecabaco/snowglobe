For agents and programs

A native instance takes jobs on the guest's root shell, whatever its app is, and a run can be bounded, stopped from outside and recorded. For many machines at once, see Orchestration.

Commands and files: sh and cp

Pass the command to snowglobe sh as one quoted argument; its flags would otherwise be read as snowglobe's own.

snowglobe run dist/python --name box --detach --runtime native
snowglobe sh box 'python3 -c "print(6*7)"'      # its output, and its exit status as ours
snowglobe sh box --json 'ls /nope'
snowglobe cp ./project box:/root/project        # files and directories, either way
snowglobe cp box:/root/project/out ./out

Each command runs with the app's environment, starting in the home directory as it would in the machine's terminal, so relative paths work; files persist for the instance's life, and $EXCLAVE_WORKSPACE names a fresh scratch directory of the command's own. Out of time (300 s, or --timeout S), the command and everything it started are killed (exit 124). What the guest sends back through cp can't write outside the destination.

A fresh machine per command: --fork

--fork makes a detached native instance a template. It restores once, and every snowglobe sh on it runs in a copy of that machine, forked in milliseconds and sharing its memory. Nothing one command does is seen by the next, so sh is all a fork instance takes: cp, exec, attach and mcp need a machine that lasts.

snowglobe run dist/python --name tpl --detach --runtime native --fork
snowglobe sh tpl 'python3 untrusted.py'         # many at once, each on its own copy
snowglobe stop tpl

MCP

snowglobe mcp <site> serves a site to an agent as an MCP server over stdio: an isolated Linux machine with run_command, write_file and read_file tools. It starts a native instance and stops it when the agent goes (--keep leaves it).

claude mcp add sandbox -- snowglobe mcp https://filipecabaco.github.io/snowglobe/python/

snowglobe mcp --daemon serves the daemon instead: an agent lists, builds and adds templates, runs commands on fresh forks or on machines it brings up, writes and reads their files, submits fire-and-forget runs and reads their results, saves snapshots, puts services behind ports, lists and checks ports, diffs and applies fleet files, and reads the daemon's status and events. SNOWGLOBE_DAEMON points it at a daemon on another host.

claude mcp add snowglobe -- snowglobe mcp --daemon

In the page: --agent, /agent/ and WebMCP

A site built with --agent (or the label snowglobe.agent="true") is one of the machines of an agent page: one page with every such runtime in it, where an agent runs commands in any of them and copies files between them, in the visitor's own tab. Nothing runs on a server, and the page is static files. It is off unless asked for. A site on several CPUs is a machine there too: the page's service worker makes it cross-origin isolated, as such a site's own page is. The labels snowglobe.agent-purpose (what the machine is good for, in a line) and snowglobe.agent-sample (a command to try) describe it on the page, and snowglobe.agent-watch (a project directory, such as /root/app) has the page show which files in it each command changed, with their diffs. snowglobe.agent-name names the machine on the page when its directory has another name: the page's Python is built from examples/python-agent (a network, for pip install) and is still python, while examples/python is the page for people, with no network.

snowglobe build examples/duckdb --agent --out dist/duckdb
snowglobe pool dist; snowglobe pwa dist/duckdb
snowglobe agent-pages dist      # dist/agent/runtimes.json, the page's scripts and service worker

snowglobe agent-pages lists the agent sites under a directory in agent/runtimes.json (from each site's run.json, read when the site is assembled) and writes the page's scripts beside it; this site's page is /agent/. Each site's own page links there (For agents, in its title strip, with ?runtime=<site>, which only preselects); an address ending #agent goes there too. ChatGPT's agent uses it today; its WebMCP (site tools) works only in the ChatGPT desktop app's built-in browser.

Open https://filipecabaco.github.io/snowglobe/agent/, choose python under Runtime, type
python3 -c 'print(6*7)' into Shell command, press Run, allow it, and tell me the exit status and output.

Each machine runs in a Web Worker of its own, so several run on several cores and the page stays responsive. The page is for agents that build and compute: Supabase (on two CPUs) and a React app on it, built with Vite and rebuilt as it changes, and Python with numpy and pandas (and pip install, which fetches wheels from PyPI through your browser), DuckDB for analytics and PostgreSQL for databases; the other runs are on the landing page, for people. A machine starts lazily, on its first command. Each one awake holds 540 to 740 MB, so only a few are awake at once: two unless the field Machines awake at once, the tool set_awake_limit or setAwakeLimit(count) changes it (1 to 8, for the page load; it runs nothing, so it asks no one). Waking another suspends the least recently used idle one first, one capture or boot at a time; a busy machine, with a job, a copy or an open preview in it, is never suspended, and a wake waits for one to finish and says so. A lower limit suspends idle machines, least recently used first, and busy ones as they finish. Suspended, a machine's state is saved in this browser (IndexedDB, a scope per runtime). Only a suspended machine's state is kept: a reload loses what an awake one did since its last suspend, and the browser asks before leaving. Start fresh… goes back to the machine as built, always after asking. A machine that fails (it powered off, its worker crashed, a capture hung) is ended at once, and its job fails; Retry starts it again. When its files can't be fetched, the page says so. The page needs the network: it doesn't work offline. Its service worker makes it cross-origin isolated (Supabase's two CPUs share memory between workers, which needs that) and carries the preview; the first visit reloads once to be loaded through it.

Where the browser has WebMCP (document.modelContext), the page registers one set of tools. Any WebMCP client can use them: a browser's built-in agent, an extension, a chat page. One added after the page starts, by an extension or a polyfill such as MCP-B's @mcp-b/global, is still found for 15 seconds, and the first drafts' provideContext works too.

One job runs at a time in each machine, and a machine's operations go in the order asked: a run asked during a copy waits for it. The first run or copy, from the form, a tool or a script, asks the person at the page to allow it, once per page load; what agents run and copy shows under Earlier runs too. In another page's frame, the page refuses to run and registers no tools. The tools are the page's own: --agent-exposed-to https://host (repeatable) shares them with other origins too, when every machine of the page shares with that origin.

Scripts on the page can use the same thing as window.snowglobeAgent: listRuntimes(), status(runtime), runCommand({runtime, command, timeoutSeconds, requestId}), readJob(jobId), cancelJob(jobId), writeFile({runtime, path, content}), writeFiles({runtime, files, move, delete}), readFiles({runtime, paths}), listFiles({runtime, path, depth}), revert({runtime, to}), runSql({sql, runtime}), buildStatus({runtime, port}), copyFile({fromRuntime, fromPath, toRuntime, toPath}), suspend(runtime), wake(runtime), startFresh(runtime), setAwakeLimit(count), openPreview({runtime, port, path}), closePreview(), previewSnapshot({maxChars}), previewInteract({actions, maxChars}) and unsaved(). Runs and copies ask the person first, as the form does. A job's output keeps its most recent 1 MiB and says when it dropped some. Jobs run with NO_COLOR=1 and TERM=dumb, and their output reads as plain text.

Jobs run as root on the guest's serial shell, beside the app, as snowglobe sh's do: the terminal never shows them. Each starts in /root, so relative paths work and files persist between jobs. Copies travel over the same serial line, as base64 in slices of a job each, so they are slow (tens of KiB a second); the target is replaced only once its sha256 checks out.

The preview: a machine's web server, in the page

A web server in a machine shows in a frame of the page: Open preview (runtime, port, path) or open_preview. Its address is /snowglobe/agent/preview/<runtime>/<port>/<path>: the page's service worker hands each request there to the agent page, which opens a TCP connection to the port on the machine's network address, writes the request as HTTP/1.1 and streams the answer back. HTTP only, no WebSockets; a server must listen on 0.0.0.0, not localhost, and pages need relative asset paths (Vite's base: "./"). The page in the frame is this site's own, so it reaches every machine's server the same way: Supabase's API is /snowglobe/agent/preview/supabase/54321, the URL to give supabase-js. While a preview is open, its machine and every machine its page reaches stay awake. Nothing is answered unless a preview is open and the person has allowed the page, and a preview address opened from anywhere but the page is refused. The service worker puts one script first in each HTML page the preview shows (preview-hook.js): it passes what the page logs, its uncaught errors and its failed requests to the agent page, which preview_snapshot reports beside the page's outline.

The two come ready and connected, and the app starts empty: web has a blank React project in /root/app (an empty page, with supabase-js set up in src/supabase.js), and Supabase has no tables of the app's yet, so the agent builds it from nothing. serve --watch builds it, serves on port 4173 and builds again on every change. Vite's hot reload needs a WebSocket, so instead the page reads the server's /__build while the preview is open and reloads the preview after each new build. The top of the page is a studio, laid out as AI app builders are: the app's live preview fills it (at desktop, tablet or phone width, with its address, Reload and New tab), with the app's Code (its files, read from the machine as they change, and each one's last change) and Database (Supabase's tables) beside it as tabs. Down its left side, the agent's steps read as a conversation: every file it edited (with the diff), command it ran, file it read, SQL it ran and build, a failed build's error over the preview, Undo last change and Revert to starter…. The page has no AI of its own: Connect an agent gives a prompt to paste into yours. The machines, with every control above, are below the studio.

The app is React 19 with Vite, Tailwind v4 and TypeScript (a tsconfig.json; .ts and .tsx build as they are, npm run typecheck runs tsc), with React Router, Zustand and clsx installed. npm install works too: in the tab, every request the machine makes is the page's own fetch(), and the npm registry allows that for plain GETs but answers no CORS preflight, which npm's own headers would need, so the machine's npm goes through a relay in serve (127.0.0.1:4874) that asks the registry with nothing but Accept. It is slow, as everything in the emulated machine is: most of a minute for one small package.

open_preview {runtime: "web", port: 4173}: the app, signed up and used in the page
list_files {runtime: "web"}, read_file {runtime: "web", paths: ["src/App.jsx", "src/styles.css"]}
write_files {runtime: "web", files: [{path: "/root/app/src/components/Todo.tsx", content: ...}, ...]}: the diffs show, web rebuilds, the preview reloads, the build's result comes back
preview_snapshot {}: the page as built, its controls with refs, and any runtime errors
preview_interact {actions: [{type: "type", ref: "e2", value: "Buy milk"}, {type: "click", ref: "e3"}]}: used as a person would, then seen again
run_sql {sql: "create table public.todos (...); alter table public.todos enable row level security; ..."}: the Data API sees it at once
On supabase: psql "$DB_URL" -c "select * from todos" shows what you added, with your user's id

The whole recipe is in llms.txt.

An idle machine doesn't stay in memory: with no job for 5 minutes, or with its tab hidden for a minute, it is suspended, its state saved and its worker ended, so the browser takes back its memory. The next command, or a key typed into its terminal, wakes it, files and all, and then runs. The terminal pages keep their machine running.

On the agent page only a suspended machine's state is kept: a reload loses what an awake one did since its last suspend (the browser asks first), and Start fresh goes back to the machine as built. Opening the app starts web, and supabase once the app uses it: up to about 1.4 GB of the tab's memory, and seconds to a minute the first time. Builds and npm install run in the emulated machine, so a rebuild takes seconds and an install of one package most of a minute.

Limits, stopping and logs

FlagWhat it doesExit
--max-runtime 30mends the run after this long, whatever it is doing124
--stop-file PATHends the run once PATH exists: create it from anywhere143
--log-dir DIRdurable console.log, serial.log and events.jsonl

Either way the job running in the guest is killed first, and a stop event saying why goes to the log. Logs are appended as things happen, so they survive a crash of the run, and rotate at 8 MiB. A named native instance logs to snowglobe/logs/<name> in your cache directory unless --log-dir says otherwise.

  • console.log: the app's terminal, byte for byte.
  • serial.log: the guest's serial line, with the kernel's own messages (an OOM kill, a panic) and the job shell.
  • events.jsonl: one JSON object a line, each synced to disk: start, restored, job_start (the command, its environment variables' names but never their values, the timeout), job_end (status, timed_out, killed, milliseconds, the first 64 KiB of output) and stop (its reason: stop-file, max-runtime, guest-stopped or end, and the exit status).

Kills reach everything a job started. A job runs in a session of its own in the guest; when it runs out of time or the instance stops, it gets TERM, then KILL after 3 s, including whatever it put in the background. A process that makes a session of its own (a daemon that setsids) is out of reach, as it would be anywhere.

A job's result is its own word. A job's exit status comes back on a line marked with a one-time value the host types only to the job's launcher, so a job that merely prints a fake result isn't believed. A job runs as root in the guest, though: one determined to can still read that value from the launcher's memory and forge its own status, output and out/ files. That reaches only its own result. The host still enforces the time limit, and if a job leaves the guest's shell busy, later jobs fail with "the guest's shell is not answering" rather than run inside it.
