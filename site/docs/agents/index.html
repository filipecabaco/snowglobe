For agents and programs

A native instance takes jobs on the guest's root shell, whatever its app is, and a run can be bounded, stopped from outside and recorded. For many machines at once, see Orchestration.

Commands and files: sh and cp

Pass the command to snowglobe sh as one quoted argument; its flags would otherwise be read as snowglobe's own.

snowglobe run dist/python --name box --detach --runtime native
snowglobe sh box 'python3 -c "print(6*7)"'      # its output, and its exit status as ours
snowglobe sh box --json 'ls /nope'
snowglobe cp ./project box:/root/project        # files and directories, either way
snowglobe cp box:/root/project/out ./out

Each command runs with the app's environment, starting in the home directory as it would in the machine's terminal, so relative paths work; files persist for the instance's life, and $EXCLAVE_WORKSPACE names a fresh scratch directory of the command's own. Out of time (300 s, or --timeout S), the command and everything it started are killed (exit 124). What the guest sends back through cp can't write outside the destination.

A fresh machine per command: --fork

--fork makes a detached native instance a template. It restores once, and every snowglobe sh on it runs in a copy of that machine, forked in milliseconds and sharing its memory. Nothing one command does is seen by the next, so sh is all a fork instance takes: cp, exec, attach and mcp need a machine that lasts.

snowglobe run dist/python --name tpl --detach --runtime native --fork
snowglobe sh tpl 'python3 untrusted.py'         # many at once, each on its own copy
snowglobe stop tpl

MCP

snowglobe mcp <site> serves a site to an agent as an MCP server over stdio: an isolated Linux machine with run_command, write_file and read_file tools. It starts a native instance and stops it when the agent goes (--keep leaves it).

claude mcp add sandbox -- snowglobe mcp https://filipecabaco.github.io/snowglobe/python/

snowglobe mcp --daemon serves the daemon instead: an agent lists, builds and adds templates, runs commands on fresh forks or on machines it brings up, writes and reads their files, submits fire-and-forget runs and reads their results, saves snapshots, puts services behind ports, lists and checks ports, diffs and applies fleet files, and reads the daemon's status and events. SNOWGLOBE_DAEMON points it at a daemon on another host.

claude mcp add snowglobe -- snowglobe mcp --daemon

In the page: --agent, /agent/ and WebMCP

A site built with --agent (or the label snowglobe.agent="true") is one of the machines of an agent page: one page with every such runtime in it, where an agent runs commands in any of them and copies files between them, in the visitor's own tab. Nothing runs on a server, and the page is static files. It is off unless asked for. A site on several CPUs is a machine there too: the page's service worker makes it cross-origin isolated, as such a site's own page is. The labels snowglobe.agent-purpose (what the machine is good for, in a line) and snowglobe.agent-sample (a command to try) describe it on the page.

snowglobe build examples/duckdb --agent --out dist/duckdb
snowglobe pool dist; snowglobe pwa dist/duckdb
snowglobe agent-pages dist      # dist/agent/runtimes.json, the page's scripts and service worker

snowglobe agent-pages lists the agent sites under a directory in agent/runtimes.json (from each site's run.json, read when the site is assembled) and writes the page's scripts beside it; this site's page is /agent/. Each site's own page links there (For agents, in its title strip, with ?runtime=<site>, which only preselects); an address ending #agent goes there too. ChatGPT's agent uses it today; its WebMCP (site tools) works only in the ChatGPT desktop app's built-in browser.

Open https://filipecabaco.github.io/snowglobe/agent/, choose python under Runtime, type
python3 -c 'print(6*7)' into Shell command, press Run, allow it, and tell me the exit status and output.

Each machine runs in a Web Worker of its own, so several run on several cores and the page stays responsive. The page is for agents that build and compute: Supabase (on two CPUs) and a Node machine with Vite to build web apps, and Python with numpy and pandas, DuckDB for analytics and PostgreSQL for databases; the other runs are on the landing page, for people. A machine starts lazily, on its first command. Each one awake holds 540 to 740 MB, so only a few are awake at once: two unless the field Machines awake at once, the tool set_awake_limit or setAwakeLimit(count) changes it (1 to 8, for the page load; it runs nothing, so it asks no one). Waking another suspends the least recently used idle one first, one capture or boot at a time; a busy machine, with a job, a copy or an open preview in it, is never suspended, and a wake waits for one to finish and says so. A lower limit suspends idle machines, least recently used first, and busy ones as they finish. Suspended, a machine's state is saved in this browser (IndexedDB, a scope per runtime). Only a suspended machine's state is kept: a reload loses what an awake one did since its last suspend, and the browser asks before leaving. Start fresh… goes back to the machine as built, always after asking. A machine that fails (it powered off, its worker crashed, a capture hung) is ended at once, and its job fails; Retry starts it again. When its files can't be fetched, the page says so. The page needs the network: it doesn't work offline. Its service worker makes it cross-origin isolated (Supabase's two CPUs share memory between workers, which needs that) and carries the preview; the first visit reloads once to be loaded through it.

Where the browser has WebMCP (document.modelContext), the page registers one set of tools. Any WebMCP client can use them: a browser's built-in agent, an extension, a chat page. One added after the page starts, by an extension or a polyfill such as MCP-B's @mcp-b/global, is still found for 15 seconds, and the first drafts' provideContext works too.

ToolWhat it does
list_runtimeseach machine: its runtime name, what it is for, its state (asleep, waking, awake, busy, suspending, failed) and a sample command
run_commandstarts command in runtime and returns its job id at once; timeout_seconds (default 300, at most 3600) and request_id (a retry returns the same job) are optional
job_statusthe job's output so far, ending [running], or as snowglobe mcp's ends: [exit N], [timed out], [stopped]
cancel_jobstops the job: its command and everything it started are killed
copy_filecopies from_path in from_runtime to to_path in to_runtime: any file up to 8 MiB, checked by sha256 on both ends; a client's cancel signal stops it
open_previewopens the page's preview on a web server in a machine: runtime, port and an optional path; returns the preview's address and what its first request got
close_previewcloses it: the machines it kept awake can be suspended again
set_awake_limithow many machines may be awake at once, count 1 to 8 (2 by default), for the page load; list_runtimes reports it as awake_limit

One job runs at a time in each machine, and a machine's operations go in the order asked: a run asked during a copy waits for it. The first run or copy, from the form, a tool or a script, asks the person at the page to allow it, once per page load; what agents run and copy shows under Earlier runs too. In another page's frame, the page refuses to run and registers no tools. The tools are the page's own: --agent-exposed-to https://host (repeatable) shares them with other origins too, when every machine of the page shares with that origin.

Scripts on the page can use the same thing as window.snowglobeAgent: listRuntimes(), status(runtime), runCommand({runtime, command, timeoutSeconds, requestId}), readJob(jobId), cancelJob(jobId), copyFile({fromRuntime, fromPath, toRuntime, toPath}), suspend(runtime), wake(runtime), startFresh(runtime), setAwakeLimit(count), openPreview({runtime, port, path}), closePreview() and unsaved(). Runs and copies ask the person first, as the form does. A job's output keeps its most recent 1 MiB and says when it dropped some. Jobs run with NO_COLOR=1 and TERM=dumb, and their output reads as plain text.

Jobs run as root on the guest's serial shell, beside the app, as snowglobe sh's do: the terminal never shows them. Each starts in /root, so relative paths work and files persist between jobs. Copies travel over the same serial line, as base64 in slices of a job each, so they are slow (tens of KiB a second); the target is replaced only once its sha256 checks out.

The preview: a machine's web server, in the page

A web server in a machine shows in a frame of the page: Open preview (runtime, port, path) or open_preview. Its address is /snowglobe/agent/preview/<runtime>/<port>/<path>: the page's service worker hands each request there to the agent page, which opens a TCP connection to the port on the machine's network address, writes the request as HTTP/1.1 and streams the answer back. HTTP only, no WebSockets; a server must listen on 0.0.0.0, not localhost, and pages need relative asset paths (Vite's base: "./"). The page in the frame is this site's own, so it reaches every machine's server the same way: Supabase's API is /snowglobe/agent/preview/supabase/54321, the URL to give supabase-js. While a preview is open, its machine and every machine its page reaches stay awake. Nothing is answered unless a preview is open and the person has allowed the page, and a preview address opened from anywhere but the page is refused.

On supabase: psql "$DB_URL" creates a notes table with row level security
On web:      a Vite page with sign-up, login and notes on supabase-js; npm run build; serve dist 4173
open_preview {runtime: "web", port: 4173}: you sign up and add notes in the page
On supabase: psql "$DB_URL" -c "select * from notes" shows them, with your user's id

The whole recipe is in llms.txt.

An idle machine doesn't stay in memory: with no job for 5 minutes, or with its tab hidden for a minute, it is suspended, its state saved and its worker ended, so the browser takes back its memory. The next command, or a key typed into its terminal, wakes it, files and all, and then runs. The terminal pages keep their machine running.

Limits, stopping and logs

FlagWhat it doesExit
--max-runtime 30mends the run after this long, whatever it is doing124
--stop-file PATHends the run once PATH exists: create it from anywhere143
--log-dir DIRdurable console.log, serial.log and events.jsonl

Either way the job running in the guest is killed first, and a stop event saying why goes to the log. Logs are appended as things happen, so they survive a crash of the run, and rotate at 8 MiB. A named native instance logs to snowglobe/logs/<name> in your cache directory unless --log-dir says otherwise.

  • console.log: the app's terminal, byte for byte.
  • serial.log: the guest's serial line, with the kernel's own messages (an OOM kill, a panic) and the job shell.
  • events.jsonl: one JSON object a line, each synced to disk: start, restored, job_start (the command, its environment variables' names but never their values, the timeout), job_end (status, timed_out, killed, milliseconds, the first 64 KiB of output) and stop (its reason: stop-file, max-runtime, guest-stopped or end, and the exit status).

Kills reach everything a job started. A job runs in a session of its own in the guest; when it runs out of time or the instance stops, it gets TERM, then KILL after 3 s, including whatever it put in the background. A process that makes a session of its own (a daemon that setsids) is out of reach, as it would be anywhere.

A job's result is its own word. A job's exit status comes back on a line marked with a one-time value the host types only to the job's launcher, so a job that merely prints a fake result isn't believed. A job runs as root in the guest, though: one determined to can still read that value from the launcher's memory and forge its own status, output and out/ files. That reaches only its own result. The host still enforces the time limit, and if a job leaves the guest's shell busy, later jobs fail with "the guest's shell is not answering" rather than run inside it.
